* General code guidelines

These are instructions for LLMs to write code more to my liking.  For general
project layout, design, and desires, see [[./README.org]].

** Documents

When authoring new content, make them ~org-mode~ files.

Use ~:exports code~ if you just want to show off the code, and don't want it to
actually run anything.

No file lists in documentation.

** Authoring Comments and Documentation

*** Formatting and punctuation

Comments must be complete sentences, wrapped at ~80 columns, with standard
punctuation.  Use two spaces after sentence-ending punctuation for easier
sentence matching.

*** Content

Only comment non-obvious intent, invariants, tradeoffs, or historical
constraints; no restating of control flow.

These rules apply to comments and documentation roughly the same.

**** Anti Pattern: Historical / Tombstone Verbiage

Historical verbiage are such as "We used to do X, but now we do Y".  We should
only provide such prose in the _surprising_ case.  These would be better thought
of as "One would typically reach for X, but it fails because of Y, so instead we
do Z".  This is the only case in which we use historical prose that refers to
prior code that no longer exists.

The easy test for this is "If you would have gotten this right on the first
pass, would this have still needed this prose?".  If the answer is no, then do
not leave historical prose.

**** Anti Pattern: Obvious Intent

Commenting intent that is obvious "This assigns foo to bar" or "This
run_workflow function runs the workflow" are simple anti patterns.  We only
comment on code that needs to be called out.  Assume the reader knows how to
write software.  If the code is self documenting, obvious code should never need
comments.

The only exception is special documentation comments on the headers of things
like functions, which then later get aggregated by a tool or auto-complete
systems.  Even then, these comments should only refer to abstract outcomes and
not implementation detail unless there is something specifically important about
that implementation.  Stating what algorithm a sort uses is fine.  Stating in
the doc comment that you used a ~loop~ over a combinator is not appropriate.

**** Anti Pattern: Inventory

Taking inventory in prose ("this does X, Y, and Z") just means you now have
extra places to account for a change.  The moment you stop doing Y, all prose
that takes inventory must be updated.  Same goes if you add a W activity.  The
simple answer is to not write this prose at all.  If you find yourself writing
these remarks, they are virtually always wrong, and instead an even briefer
summary must be written instead, or the comment must be removed entirely.

**** How to Summarize

This covers any summarized activity (function headers, file headers, and so on).

A summary details what the outcome of the activity is, and never the steps
involved unless those steps are particularly surprising.  A "fire the nukes"
script shouldn't include anything about arming the nukes, aiming the nukes,
authorizing the nukes, or anything else that we _do_ to fire the nukes unless
there's some specific quirk that truly needs calling out that is _relevant to
that summary_.  A good summary for a ~nuke-fire.sh~ is "Fires the nukes.".

***** Documenting Quirks and Surprises

Most quirks in a function or script needn't make it to the summary.  Let's say
that we generally expect these steps for any nation to fire its nukes:

1. Arm the nuke.
2. Aim the nuke.
3. Authorize the firing of the nuke.
4. Fire the nuke.

Any nuke firing activity here wouldn't be in a summary.

Let's say our nation requires the tips to be signed using the public key of the
recipient.  So now our script looks like:

1. Arm the nuke.
2. Aim the nuke.
3. Sign the tip with the recipient's public key.
4. Authorize the firing of the nuke.
5. Fire the nuke.

Okay that's an odd step, and because it's an odd step, it would require a
comment _immediately adjacent_ to that specific functionality.  Since this has
no great impact on how our ~nuke-fire.sh~ script works, we should leave it out
of the summary.

** Code

*** Command-line JSON

Use ~jq~ for parsing or producing JSON from shell scripts and ad hoc CLI
invocations.  Do not reach for ~python -c 'import json; ...'~ or other
language runtimes — ~jq~ is universally available on shells provisioned by
this repo (added as a ~runtimeInputs~ entry on each consuming derivation,
or via ~environment.systemPackages~ on hosts that need it broadly), reads
better in pipelines, and composes naturally with the rest of the standard
shell toolkit.

*** initialisms

Use Pascal Initialisms (~Url~) instead of Preserved Initialisms (~URL~) when
_authoring_ new identifiers in camel case.

** COMMENT Code Review Workflow

*** Automatic Review Process

When making code changes in this repository, Claude must proactively invoke
the code review agents:

1. After creating or modifying any files, use the Task tool to invoke
   ~standards-reviewer~ to check CLAUDE.md compliance.
2. Use the Task tool to invoke ~senior-engineer~ for engineering best
   practices review.
3. Create review reports in ~reviews/{date}-{sequence}/~ directory with
   org-mode formatting.
4. Present findings and suggest fixes before continuing with other work.

This review process is mandatory for all code changes unless explicitly told
to skip reviews.

** Network and Hosts

The local network uses the ~.proton~ domain suffix.  Host names declared in
~nixos-modules/facts.nix~ are reachable at ~<hostname>.proton~ (e.g.
~rubidium.proton~, ~scandium.proton~).  When SSH-ing to a host by short name,
append ~.proton~ — e.g. ~ssh rubidium.proton~.

** Nix

*** Flake Inputs

Try to keep Flake inputs in lexicographical order.

When adding an new input, you don't need to include it in the outputs section
unless it's specifically required in that section.  This is afforded due to
~flake-inputs~ being aggregated and passed into the hosts using ~specialArgs~.

*** File Layout

There are both ~<system-type>-configs~ and ~<system-type>-modules~, where
~<system-type>~ is one of ~nixos~, ~darwin~, or ~home~.  This corresponds with
whether or not it belongs to NixOS, macOS, or Home Manager.

~configs~ are inert sets of configuration.  They could use functions to
calculate or compose settings, but the act of importing the config is what
activates said config.  These files do not include ~config~ or ~options~
attributes.

~modules~ are configurable option sets.  They use ~config~ and ~options~
attributes.  Importing one of these simply makes the options available, and by
itself doesn't change anything for a host's configuration.

I do have some inconsistencies wherein some ~nixos-modules~ are actually
~nixos-configs~, but I didn't have the split pattern at time of authorship of
those.

*** Deploying

Deploy through ~proton-deploy~.  It is not a thin alias — it carries deploy
logic of its own, and will carry more over time.  Do not invoke the tools it
wraps directly, and do not hand-roll steps around it (including a separate ~nix
build~ of a host's system derivation as a "pre-build" or dry run); anything
reimplemented by hand silently skips the rest of it.  If it seems to be missing
something you need, add it there rather than working around it.

The ~remote-deploy~ break-glass cases documented under [[file:./README.org::*deploy tools][deploy tools]] are the
exception.  Return to ~proton-deploy~ once recovered.

*** Nix Build

A ~nix build '.#nixosConfigurations.${host}.config.system.build.toplevel'~
invocation is almost assured to fail because there will likely be a mismatch
between architecture and platform.  See [[file:./README.org::*deploy tools][deploy tools]] for how to do a deployment,
which will also do your build.

*** Scripts

Scripts that ship as part of a derivation are co-located with their
~default.nix~ in a subdirectory under ~derivations/~, following the same
convention as ~nixpkgs~.  The directory name, the script file name, and the
derivation's ~name~ (or ~pname~) must all match.

The script file carries a shebang appropriate to its language so that editors
recognise it and it can be executed directly outside of Nix (given the right
interpreter and dependencies on ~PATH~).  Use the appropriate ~writers~ function
for the script's language — no custom ~installPhase~ needed.  Each writer
handles the shebang, installs the binary, and runs a linter at build time
(~shellcheck~ for shell, ~pyflakes~ for Python): ~writeShellApplication~ for
shell scripts, ~writers.writePython3Bin~ for Python.

#+begin_src
derivations/
  my-tool/
    my-tool       <- script with shebang; runnable directly
    default.nix   <- derivation; patches shebang, wires runtime deps
#+end_src

The older pattern of a bare ~.nix~ file in ~derivations/~ reading its script
from ~../scripts/<name>~ still exists for historical scripts, but new scripts
should use the co-located layout above.

*** Secrets

Secrets are managed with agenix-rekey.  Only specify ~rekeyFile~ when there is
a strong reason to control the output path (e.g. a secret that must live
alongside a specific config file).  For generated secrets, omit ~rekeyFile~
entirely — agenix-rekey will place them under ~secrets/generated/~
automatically, which makes it easy to identify which secrets are generated vs.
manually managed.

**** Secrets for systemd Units

Bind agenix secrets into systemd units using ~LoadCredential~ rather than
setting ~owner~ on the secret.  Systemd reads the source file as root and
exposes it under ~/run/credentials/<unit-name>/<credential-name>~, readable
only by the service — no ownership tuning required.  This is also the only
correct approach when the service uses ~DynamicUser = true~, where no stable
uid exists to assign ownership to.

The consuming application config (e.g. ~password_file~, ~credentials_file~)
must reference the ~/run/credentials/<unit-name>/<credential-name>~ path, not
the raw agenix path.

#+begin_src nix :exports code
  age.secrets.my-secret = { };  # no owner needed

  systemd.services.my-service.serviceConfig.LoadCredential = [
    "my-secret:${config.age.secrets.my-secret.path}"
  ];
#+end_src
