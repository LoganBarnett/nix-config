#+title:     Notifications
#+language:  en

* Overview

Rationale for the household push-notification stack.  Self-hosted services
in this network (download completions, backup outcomes, alertmanager
firings, IoT events) need a way to reach phones and desktops without
each service inventing its own delivery mechanism.

Posture:

- Self-hosted preferred; data flowing through a third party is reserved
  for cases where the alternative is materially worse.
- iOS support is required.  Household uses iOS, so a delivery agent
  with no usable iOS client is disqualifying.  First-party iOS support
  is preferred over a community port — the latter is operative until
  the maintainer loses interest.
- The stack should be declarable in Nix.  Click-ops administration of
  notification sources is a hard negative; every new source should be a
  config commit, not a web-UI round trip.

* Options considered

** ntfy.sh (chosen)

Topic-based pub-sub.  Anyone holding the URL =https://ntfy.host/topic=
publishes; anyone subscribed to that topic receives.  Single static Go
binary, embedded SQLite, web UI bundled.

What recommended it:

- Native iOS *and* Android apps.
- Topic semantics fit "I have many services that want to alert me"
  naturally: pick a topic per source, drop the URL into the source's
  config, done.  No app/token registration round trip.
- Authentication is opt-in.  The server runs with =auth-default-access:
  read-write= and zero credentials for personal use, or locks down with
  users + per-topic ACLs when the topology calls for it.
- User and ACL management ships as =ntfy user= and =ntfy access=
  subcommands.  That made it tractable to add a reconciler later — see
  [[https://github.com/LoganBarnett/nix-hapi-provider-ntfy][nix-hapi-provider-ntfy]] — without driving the web UI.

** Gotify (declined)

DB-backed notification server with first-class *applications*: each
notification source is registered as an application in the web UI,
issued a token, and that token goes into the source's config.

Why declined:

- iOS support is community-only.  The official Gotify project ships
  Android and web clients; iOS coverage exists but as a third-party
  port.  Not disqualifying on its own, but it tilts the platform-risk
  ledger compared to ntfy's first-party iOS app.
- The application/token model means every new source is a click-ops
  round trip through the web UI to create the app and copy the token.
- Token administration is fully web-UI-driven.  No CLI means no
  reconciler — every change to the auth surface is a manual operation.

The application model has real value when each source needs distinct
authorisation in a multi-tenant deployment.  In a single-household
setting that benefit is invisible and the friction is constant.  Even
with the community iOS client in the picture, the click-ops + no-CLI
combination would carry the decision on its own.

** Pushover (declined)

Commercial hosted service.  Per-device one-time app purchase, HTTP API
for sending.

Why declined: it is a third-party SaaS for data that does not need to
leave the network.  Volume isn't high enough to make hosted delivery
attractive, and the privacy / availability trade-off is in the wrong
direction for the use case.

** Apprise (declined; wrong category)

Notification *router* — a library / CLI that fans out to many backends
(Discord, Slack, Pushover, Telegram, …).  It solves a different
problem: "given multiple destinations, how do I address them
uniformly?"  The choice this document is about is what the
*destination* is.  Apprise could sit upstream of ntfy if the
household ever needs a multi-destination fan-out, but it is not itself
a delivery target.

* iOS notification tier ceiling

A wrinkle worth documenting up front, because it caps what any
self-hosted notification stack can deliver to an iOS phone right now.

iOS distinguishes three interruption tiers:

1. *Normal* — silenced during any active Focus mode.
2. *Time-Sensitive* — what ntfy's ~X-Priority: 5~ triggers.  Pierces
   Focus modes /by default/, but only when the receiving Focus has
   "Allow Time-Sensitive notifications" enabled for ntfy (per-app,
   per-Focus).  Sleep Focus is the case to watch: a strict Sleep Focus
   configuration will silence Time-Sensitive notifications, so a
   3 AM disk-full alert can be muted unless the user has explicitly
   allowed Time-Sensitive from ntfy in the Sleep Focus settings.
3. *Critical Alerts* — pierces DND, Focus modes, and the mute switch
   unconditionally.  Requires a per-team entitlement granted by Apple;
   it is not a capability any developer can simply enable.

ntfy's current state on this:

- Apple has /already granted/ binwiederhier's developer team the
  Critical Alerts entitlement.
- The capability isn't yet wired into the iOS Xcode project, so
  shipped ntfy iOS builds still max out at Time-Sensitive.  See
  ntfy issues [[https://github.com/binwiederhier/ntfy/issues/1680][#1680]] (improvement plan), [[https://github.com/binwiederhier/ntfy/issues/1235][#1235]] (Critical Alerts
  request), and [[https://github.com/binwiederhier/ntfy/issues/1431][#1431]].  Roadmap rank: Priority 2A behind reliability
  fixes.  No PR or shipping timeline as of the time this doc was
  written.
- A locally built iOS app cannot unlock Critical Alerts: the
  entitlement is bound to binwiederhier's developer team, not
  transferable to a personal team ID.  A personal build can only ship
  with whatever entitlements the personal team has, which won't
  include Critical Alerts unless separately granted by Apple.

Commercial-SaaS alternatives that /do/ ship with Critical Alerts:
Pushover, PagerDuty, Opsgenie, VictorOps.  All proxy data through
their own infrastructure, which violates the self-hosted posture
established above.  The pragmatic middle ground if a household
genuinely needs guaranteed wake-up reliability is to route
~severity=critical~ alerts through Pushover-for-iOS while letting
ntfy handle everything else; AlertManager can do this fanout
declaratively with a single routing tree.

Until ntfy ships the Critical Alerts wiring, the de facto severity
contract is:

- ~X-Priority: 5~ → Time-Sensitive on iOS / high-priority on Android.
  Reliably pierces default Focus modes; user-configurable Sleep
  Focus may still silence it.
- Lower priorities → Normal delivery, silenced during Focus modes.

No special handling of mute switch or DND is currently reachable from
ntfy.  Plan AlertManager severity routing accordingly: assume
Time-Sensitive is the loudest hammer in the toolbox.
